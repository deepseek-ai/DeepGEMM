# SM120 heuristic calibration

SM120 GEMM layout selection ranks valid tile candidates with this latency model:

```text
tma_per_kblock = tma_bytes_per_kblock * kCyPerTmaByte
                 + kSyncBaseCy / sqrt(num_stages)
block_time = effective_kblocks * tma_per_kblock + kBlockOverheadCy
latency = effective_waves * block_time + split_k_reduction_cycles
```

The three constants were introduced by an empirical 164-point SM120a tile
sweep in commit
[`1383f15`](https://github.com/deepseek-ai/DeepGEMM/commit/1383f15d524d929059f7f4b11489e08d6b793ef2):

| Constant | Default | Model role |
| --- | ---: | --- |
| `kCyPerTmaByte` | `0.07` | Effective TMA cost per input and scale-factor byte. At the original tuning clock, this corresponds to roughly 35 GB/s per SM. |
| `kSyncBaseCy` | `120` | Per-K-block barrier cost before the pipeline-stage discount. More stages reduce this term by `sqrt(num_stages)`. |
| `kBlockOverheadCy` | `2000` | Per-wave intercept for epilogue and scheduling work not represented by TMA traffic. |

These are ranking coefficients, not architectural constants. Only their ratios
affect candidates without split-K. GPU SKU, clocks, power state, datatype,
epilogue, and shape distribution can change fitted values.

## Calibration harness

Build DeepGEMM from the source under test, then run:

```bash
python -m pip install numpy
./develop.sh
python scripts/calibrate_sm120_heuristic.py \
    --dtype fp8 \
    --cache-policy steady \
    --output sm120-fp8.jsonl
```

The script requires an SM120 GPU. It runs calibration and held-out validation
shapes, enumerates candidates generated by the SM120 heuristic, rejects
incorrect outputs, and records CUDA-event timing samples. Each candidate runs
in a separate process with `DG_JIT_FORCE_LAYOUT=BMxBNxBK`, so JIT memoization
cannot reuse a different layout.

The fit uses within-shape centered features. This removes shape-specific timing
intercepts, then applies nonnegative least squares to TMA bytes, barrier work,
wave count, and the fixed split-K term. Output includes:

- raw samples and median latency for every valid candidate;
- device, driver, clock, build SHA, seed, and cache policy;
- feature rank, condition number, and relative median absolute deviation;
- fitted constants when the fixed-cycle scale is identifiable;
- current-model and fitted-model selection regret on held-out shapes.

Use repeated `--shape MxNxK` arguments to calibrate another workload. First two
thirds form the fit set; remaining shapes form the validation set. Use distinct
`--seed` values across sessions to change candidate order and tensor data.

`steady` measures repeated launches after warmup. `cold` flushes a 256 MiB
buffer before each measured launch. Do not compare these policies directly.

## Interpreting results

Run on an idle GPU with stable clocks and thermals. Record multiple sessions and
reject a run when relative timing dispersion is large or the feature matrix is
poorly conditioned. Compare selection regret, not coefficient fit alone.

Results from one GPU SKU support local diagnosis only. Changing defaults needs
repeatable held-out improvement across representative shapes and more than one
SM120 SKU. Keep per-SKU results separate; RTX 5070 Ti measurements, for example,
must not be presented as general SM120 tuning.
